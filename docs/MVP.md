# MVP 定义

## 1. 目标

MVP 要证明以下闭环：

> 运营者签发客户端凭证 → 野人音乐提交一首曲目观测 → 中央目录查询 → 缓存未命中时调用一个 Provider → 返回可解释候选 → 用户在 NAS 本地确认和写回。

## 2. 端到端切片

### 2.1 客户端接入

- 运营管理员创建、查看和撤销客户端安装凭证。
- 完整 Token 只显示一次，数据库只保存摘要。
- 野人音乐使用 Bearer Token 调用客户端 API。
- 每个请求绑定客户端身份、限流和 Request ID。

### 2.2 曲目解析

- 野人音乐提交 `clientTrackId`、文件名、现有标签、时长、格式和可选指纹。
- 服务端不接受绝对路径或完整音频文件。
- `Idempotency-Key` 防止网络重试产生重复任务。
- 解析请求是持久任务，支持 queued、matching、matched、no_match 和 failed。

### 2.3 中央目录与缓存

- 建立 Artist、Release、Recording 和 Track 规范实体。
- Provider payload 保存为不可变来源观测，包含来源 ID、抓取时间、过期时间、payload hash 和适配器版本。
- 已有目录优先匹配；未命中才调用一个合规 Provider。
- 相同查询合并上游请求，并对未命中结果做短期负缓存。

### 2.4 候选与本地写回

- 候选至少比较标题、歌手、专辑、时长、曲号和版本关键词。
- 返回字段级证据、冲突、来源和置信度。
- 用户确认和文件写回由野人音乐执行。
- 野人音乐可回报接受、拒绝和写回结果，中央服务不访问文件。

## 3. 数据边界

默认允许提交：

- 客户端生成的曲目 ID
- 文件名，不含绝对目录
- 标题、歌手、专辑、曲号等现有标签
- 时长、格式和可选音频指纹

默认禁止提交：

- NAS 绝对路径和网络地址
- 完整音乐或未授权的音频片段
- 用户密码、播放历史、歌单和野人音乐数据库
- Provider Cookie 或用户个人平台凭证

## 4. 技术边界

- MVP 单节点使用 SQLite，验证真实流量后、开放大规模接入前迁移 PostgreSQL。
- Web 管理端只供运营者管理客户端、Provider、缓存和任务。
- 野人音乐是最终用户交互和本地文件操作端。
- MVP 只接一个 Provider，不提前实现插件系统或跨节点 Worker。

## 5. 非目标

- 公开注册、邮件验证、订阅计费和多角色团队。
- 主动抓取所有歌手、专辑和歌曲。
- 歌词、封面、音乐下载、转码和在线播放。
- 中央服务直接写标签或控制 NAS 文件系统。
- 自动接受所有候选。

## 6. 验收标准

- 撤销后的客户端 Token 立即不能提交请求。
- 相同客户端和幂等键只产生一个解析请求。
- 缓存命中不访问 Provider；并发未命中只访问一次。
- Provider 超时、429 和结构变化有稳定错误类别。
- 候选能够说明匹配和冲突原因。
- 不同客户端不能读取彼此的请求或观测。
- Bun、Go 和 Docker 构建通过，数据库升级使用不可变迁移。
